# 亦玩客资管理

第一版支持公司用户名/密码、管理员建号与停用、四类来源导入、运营批量分配、业务员独立客资视图、跟进历史、重复核查。暂不支持转交与各平台实时同步。

## 使用

管理员先在「账号与权限」创建运营和业务员，姓名与表格原业务员姓名一致。运营在「导入客资」选择来源与工作表，预览并确认。表格包含分配业务员时直接保留归属；创建对应姓名的业务员账号后自动关联客资，疑似重复也保留负责人。没有负责人的新增客资才进入待分配。VIP、A、B、C手动选择，未评级保留空值；分类看板按登录账号权限显示。

手机号仅按数字做疑似重复提示，不猜测国家区号。原始来源、需求、跟进状态及收件箱链接保存在详情里。完全相同的导入记录跳过，跟进不影响重复导入判断。

## 本地运行

需要 Node 22.13+。安装依赖后运行 `npm run build`，对生成的本地D1配置应用 `drizzle/0000_common_lorna_dane.sql`，运行 `npm start -- --port 8787 --var INITIAL_ADMIN_PASSWORD:<本地初始密码>`。首次登录 admin 创建管理员。正式初始密码通过 Sites 密钥配置，不写入源码。

数据库迁移：`node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_common_lorna_dane.sql`

## 验证

`npx tsc --noEmit` 验证类型；`python3 tests/workflows.py` 对一次性本地数据库验证权限与主要业务流程。测试不用于生产，重复运行前使用全新测试数据库。

## 托管与数据

Cloudflare D1 保存账号、客资、分配和跟进，R2 保存工作台快照、大型操作结果和附件；数据库、对象内容及备份不进入 Git。站点入口允许持有链接者打开，公司账号登录后才可读取数据。登录会话12小时有效，停用会立即撤销会话。初始管理员登录后应修改密码。定期备份及独立域名待公司确定。

每次导入最多3000条，列表当前最多10000条；更大规模需增加服务器分页。支持客户档案云端附件上传和下载；无客户删除、自动合并或跨平台聊天同步。表格文件在浏览器本地解析，确认后只提交所选工作表字段。

## 广告投放

管理员与运营可新增和更新投放记录，包括平台、广告名称、日期、负责人、进度、预算、实际花费和备注。阿里、抖音本地推固定使用CNY；Meta、谷歌固定使用USD。金额以整数分保存，汇总按币种分别统计，不自动换汇。业务员不可访问广告记录。已保存记录不能改到另一币种的平台，避免已有金额被重新解释。

验证：`node scripts/test-advertising.mjs`。

## Winnie 网页工作台（本地收发连接）

管理员可切换老板／Winnie视角。操作保留真实账号审计，服务端检查当前客户归属。网页按客户会话、聊天消息、回复输入和客户资料组织，支持原工作台场景、建议回复、改写、翻译、批准资料发送和单客户自动接待暂停／恢复。

收发由本机工作台 2.0.6 执行，不在网页保存 WhatsApp、邮箱或模型凭证。电脑须保持开机、联网且工作台运行。网页每5秒检查连接，超过30秒无心跳即显示离线；当前会话约每8秒获取一次最新消息，邮件在当前会话查看时至多每分钟同步一次，也可手动刷新。离线不能提交新操作；排队超过60秒的操作不执行。已领取操作不自动重新领取；结果不明不得自动重发。

老板视角的“生成本地收发连接配置”生成一次性展示的设备令牌并使旧令牌失效。配置放在工作台 userData/crm-bridge.json，文件权限600；私有 Sites 的 siteToken 仅由公司管理员配置在本机，不进入网站源码或浏览器。只有固定公司站点与本地8796测试地址被允许。新设备连接默认关闭，配置 enabled=true 后启用。禁用配置后停止收发连接；原工作台独立运行。

已连接时每分钟刷新原工作台客户目录、分类、群聊和场景；旧导出文件仅作为归档导入入口。实际打开会话后通过本地连接读取当前消息，并执行真实发送。最近80条消息以文字显示，单条最多2000字符；原始历史、音视频和附件仍完整保留在桌面。CRM客资与已有桌面客户需人工核对关联，不自动合并客户。网页草稿不覆盖桌面草稿；如桌面存在未发草稿，需勾选保留原稿、仅发送网页消息，且发送前仍校验桌面版本。

邮件保留已确认公司签名，核对发件账号、收件人和正文；只有已发送项回执才标记成功。首次联系专用的完整附件流程仍由原工作台管理，不自动替代。自动回复继续使用原工作台已有的 WhatsApp 接待规则，不另起自动回复引擎；不会自动打开总开关或扩展客户范围。

测试：`node scripts/test-workbench.mjs` 验证权限、数据保留、设备认证、离线、队列去重和结果隔离。`scripts/test-workbench-http.mjs` 仅可在空的隔离本地数据库执行。桌面侧新增 `scripts/check-crm-bridge.cjs`、`scripts/check-crm-mail.cjs`，并运行原发送、接待和邮箱检查。

## 客户管理与档案

支持 VIP/A/B/C 分类筛选、客户新建和编辑、批量分类和项目阶段。修改只提交变化字段，原工作台校验客户归属、版本冲突与重复联系方式后保存，不替换整份客户数据。

客户档案提供项目进展、交接记录、分页沟通历史和已有附件目录。新增记录保存在原工作台 project-records，原桌面档案也可查看；原本机附件清单保留；新增云端附件直接上传 R2，数据库仅保存名称、大小、归属与下载链接。

场景管理为独立的列表与编辑器页面，沿用原场景规则。公司场景仅管理员可修改并保存到原工作台；业务员可在聊天编辑框调整本次话术。聊天支持中文写作翻译、逐条消息翻译、已有群聊、独立发送已批准产品资料。

验证：类型检查、角色隔离/批量归属/命令幂等测试和桌面完整检查通过；本地实际验证客户字段写回与恢复、交接记录、中文写作、聊天翻译及已有群聊读取。未向真实客户或群聊发送测试消息。

## 自有 Cloudflare 部署（2026-10-21）

- GitHub：`https://github.com/Yifunlife/CRM`，使用 `main`。
- 网站：`https://yifun-crm.yifunlife.workers.dev`。
- D1：`yifun-crm-db`，绑定 `DB`；R2：`yifun-crm-files`，绑定 `BUCKET`。均与其他业务系统隔离。
- `npm run deploy:cloudflare` 只构建和部署程序，不运行数据库迁移、初始化、导入或 R2 文件上传。数据库结构升级通过 `npm run db:migrate:cloudflare` 单独执行。需要先在自己的终端完成 Wrangler 登录。Cloudflare 的 Git 构建可使用构建命令 `npm run build:cloudflare`，部署命令 `npm run publish:cloudflare`，根目录为本仓库根目录。
- 原 Sites 地址可通过运行时变量 `CRM_BACKEND_ORIGIN=https://yifun-crm.yifunlife.workers.dev` 转发到新站，保留原访问限制和桌面工作台地址。新 Cloudflare Worker 不设置此变量。切换前校验数据并迁移有效登录会话；切换期间短暂停用桌面 CRM 连接，切换后恢复。桌面工作台仍负责本机 WhatsApp／邮件收发。
- D1 不保存图片、二进制或 Base64 文件。工作台快照只保存 `{"$r2":"records/..."}` 引用；超过16KB的操作结果采用相同方式。旧版内嵌 JSON 可读取，迁移后统一使用新引用。附件单文件限100MB，按流上传，下载时重新校验账号和客户归属；R2 桶保持私有。
- 管理员在「账号与权限」下载完整数据库备份；包含账号密码哈希和业务数据，应按敏感备份保存，不上传 GitHub。备份会还原 JSON 引用内容，但不包含附件二进制；有云端附件时还需单独备份 R2。
- `scripts/import-cloudflare-backup.mjs` 仅用于首次迁移：先校验完整结束标记、表计数与外键；大型 JSON 按 SHA256 去重上传并下载比对；再写入 D1 并逐字段校验。未执行队列取消，执行中任务改为待核实，不重放历史发送。已有附件或加密 Google 凭证时会停止，要求先迁移对应对象／密钥。
- 备份、迁移报告和本地凭证不在仓库中；旧站数据库暂保留为回退副本，不自动删除。

验证：`node scripts/test-workbench.mjs`（R2 引用兼容、缺失对象、上传下载字节、归属隔离、大小限制），以及原分配、运营、广告测试和类型检查。

## main 自动部署

Cloudflare Workers Builds 连接 `Yifunlife/CRM` 的 `main`，构建命令为 `npm run build:cloudflare`，部署命令为 `npm run publish:cloudflare`。自动部署仅更新 Worker 程序和网页静态资源，继续绑定现有 D1 `yifun-crm-db` 与 R2 `yifun-crm-files`；不执行数据库迁移、清空、种子数据、备份导入或对象覆盖。涉及数据库结构的更改应先单独审核迁移并备份，再执行 `npm run db:migrate:cloudflare`。
部署前会核对生成配置中的 Worker、账号、D1 数据库 ID 和 R2 桶名；不匹配时停止发布，防止误接到其他数据资源。

## 订单跟单（2026-10-22）

「订单跟单」采用紧凑列表、右侧订单详情及辅助阶段看板。按已确认职责提供12个阶段、逐项核对、待办与异常、物流节点、附件、操作历史和每日汇报草稿。跟单可关联现有成交记录，也可按合同编号关联已有CRM客户建立；不会自行增加成交统计或修改客户归属。报价、核算及商务／财务确认仅留存编号与证据，不替代其他系统的核算、付款或授权审批。

管理员在跟单页面「后勤账号」指定现有账号。管理员与指定后勤维护全部跟单，业务员仅查看本人商务归属订单；后台和附件下载均检查权限。指定后勤会获得全部订单跟单的维护权限，其他模块仍按原角色处理。

业务日期及汇报按北京时间。计划发货前10天、预计到港前7天产生站内待办，已不足规定天数时立即进入提醒。日期变更必须填写原因并保留原日期；已完成对应核对但日期变化时重新提示复核。待办需记录处理背景、联系回复、下一步、负责人、预计完成与下次反馈时间；金额事项解决前需保存商务提前告知和有权限人员确认记录。未解决事项、未完成阶段及未复核的物流日期会阻止订单归档。归档后只读，需填写原因重新打开。

第一阶段按下方 2026-10-26 范围执行。大小周起点、工作时段及紧急响应时限待配置，不据此认定违规。提醒只发至CRM站内通知箱，邮件未启用；每日汇总由系统生成，并逐项目保存人工核对状态。

新表使用 `0012_wild_kulan_gath.sql` 增量创建，原表不改动。附件存于原R2桶的 `order-attachments/` 前缀，数据库保存元数据；完整数据库备份包含新表，附件二进制需随R2单独备份。`node scripts/test-order-followup.mjs` 验证权限、阶段、并发、日期、归档及原数据保护。

### 历史项目批量导入

管理员或指定后勤在「订单跟单 → 批量导入」下载CSV模板，上传XLSX或UTF-8 CSV，选择工作表、匹配列并预览后确认。每批最多500条，预览不写入；待修正行会阻止整批提交。导入只新增，按去除首尾空格、不区分英文大小写的订单号跳过已有或本文件重复记录；确认时重新匹配当前CRM数据，订单与导入审计在同一事务写入，重试不会重复建单。

项目名称、合同／订单编号必填，客户通过CRM客户ID或准确名称匹配；重名时需指定ID或商务负责人，客户必须已分配启用的商务账号。后勤负责人须为管理员或已指定后勤，可在弹窗选择默认后勤。未匹配客户不会自动创建，原客户归属与成交统计不改变。

当前阶段支持1–12或完整名称；历史说明保留，前序阶段不自动完成，历史“已完成”描述也不自动触发归档。表格日期支持标准文字日期与Excel数值日期（包括1904日期系统）；导入时间不冒充原信息确认时间。后续编辑时保留历史说明及待核实的原日期信息。`node scripts/test-order-import.mjs` 覆盖整批校验、500条导入、重复重试、回滚、身份匹配及历史数据保护。

## 管理端与业务端入口

管理端「客户管理」包含客资总览、全部客资和客资分配；分类看板已并入客资总览，保留VIP、A、B、C、未评级统计及点击筛选客资的操作，权限保持一致。业务端入口为 `/sales`，与管理端共用账号和数据；业务员登录后进入业务工作台，仅保留「客户沟通」「我的客资」「跟进情况」三个主入口。

业务端「跟进情况」展示订单项目进度，直接读取后勤维护的同一份跟单数据，不另建项目副本。普通业务员仅查看其商务归属订单，后台继续检查订单与附件权限；刷新即可读取最新阶段、事项、物流及文件。已获指定后勤权限的账号仍按原授权维护跟单。


## 跟单第一阶段（2026-10-26）

在原订单档案上扩展，不新建客户或订单副本，不改变原12个阶段编号。新增「跟单记录」按事项发生时间展示订单交接、设计工程、工厂、验货、整改复验、货代、装柜发货、单证报关、在途到港、收货安装、完成归档11类记录。每条记录保留录入人及录入时间；通过「继续跟进」追加后续记录，原记录不覆盖。旧记录仍保留在原阶段、待办和操作历史中。

- 已完成事项可直接记录结果。未完成事项必须填下一步、责任人、期限和约定跟进时间，自动建立待办；关联原待办追加记录时更新同一事项。验货和整改复验有独立必填资料。阶段完成及归档仍受未解决事项校验约束。
- 金额按最小货币单位存储，保留原因、金额、币种、差额、待确认／已确认、确认人及凭证。确认人限本订单商务或管理者，后勤登记确认事实；不代替付款或发货审批。待确认金额不能结案。历史非结构化金额记录原样保留，继续登记时需补全结构化信息。
- 预计发货、实际发货、预计到港、预计现场送达及安装日期分别维护，另有预计验货节点；修改或清空原日期需要原因，并保留前后值、修改人、时间。聊天、邮件或已有资料可关联HTTPS原链接；已上传订单附件直接勾选，不重复上传，原系统权限不变。
- 订单首页展示在办、待确认、异常、逾期、未来10天节点、更新时间、最近跟进内容及今日核对状态。「每日汇报」汇总当天过程记录、补录记录、资料变更、待确认、异常、临近节点和未结事项；逐项目核对补充一次，核对后发生新变更会提示重新核对。
- 顶栏「通知」供每个登录账号查看本人通知并确认已读；有全公司跟单查看权限的管理者可查看全部收件人与送达状态（最近200条）。渠道固定为CRM站内，区分已入通知箱／未读／已读及条件解除。邮件未启用，不自动联系客户。
- Worker每天北京时间08:00检查到期提醒；通知箱只读取已生成的通知。付款、审批、金额和异常等操作通知即时生成。发货前10天、到港前7天、任务约定时间、任务逾期、金额待确认、异常与紧急事项有对应接收人。逾期通知任务负责人及管理者；金额和异常通知商务及管理者；紧急事项通知本项目跟单人，有有效代办时转给代办。相同提醒按条件与收件人去重，已读状态不会因刷新清空。条件解除后保留历史。
- 不产生跟单自动扣分、KPI等级或绩效工资，不自动追溯扣分，不调用或改写现有分配及业绩规则。大小周起点和紧急响应时限继续待配置。
