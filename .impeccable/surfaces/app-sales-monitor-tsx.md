# 智能监控 · Sales Monitor

## Purpose and direction

为管理者提供全团队流程核查入口，为销售提供本人记录的处理入口。以已保存的客户、项目、报价、合同、订单和连接记录呈现问题依据、责任人、建议与原业务页面入口，帮助用户判断下一步。异常表示需要核查，不表示已证实业务失误。

沿用现有蓝白 Operate 操作后台，不建立新的视觉体系。全局品牌、导航、按钮与面板以 `DESIGN.md` 及现有后台为准；本文件只约束 `app/sales-monitor.tsx`、`app/sales-monitor.css` 及其 `app/customer-entry-monitor.tsx` 客户规则区这一表面。`PRODUCT.md` 保持不变。

## Layout and visual rules

- 内容区最大宽度 1320px，居中；标题“智能监控”、说明和“刷新监控”置顶。
- 首屏依次显示读取范围及北京时间、四项范围摘要、到期检查与报价来源状态，再进入客户六项规则与“其他问题分类”。摘要包括销售项目、执行中订单、新增待首次联系和异常事项；项目数按服务端返回的项目记录统计，不额外解释为活跃项目数。
- 客户规则区沿用同一白色面板、蓝灰文字及细分隔线，默认只展示固定六项规则名称及各自数量，零值也保留。规则说明移入所选规则明细；默认不展示客户、依据、建议或空态明细。点击规则按需读取明细，“收起明细”返回分类数量视图；切换规则回到第一页。规则区独立于其他问题的筛选及每页 30 条明细分页。
- “其他问题分类”默认只展示分类名称与数量；点击分类才显示该类连续明细列表，“收起明细”返回分类数量视图。每条明细保留原处理类型、流程环节、责任人、标题、依据、建议及“去处理”入口；聚合事项保留记录条数。正文宽度不超过 75ch，长文本可换行，行动按钮不压缩。
- 类型与环节使用文字，只有异常额外使用红色 `#a62b26`，不能仅靠颜色表达状态。正文与次要文字沿用后台蓝灰色；摘要数字使用深蓝 `#183765`。白色面板、细分隔线承接现有后台。
- “筛选统计范围”默认折叠，展开后筛选依次为处理类型、流程环节、负责人（仅全团队范围）和搜索；搜索匹配事项标题、依据、负责人，不承诺搜索所有业务字段。修改任一筛选返回第一页。
- 其他问题按稳定检查编号前缀分组：首次联系、下一步计划、报价同步与接收、合同交接、关联报价、合同订单关联、放行、沟通连接及项目到期提醒。订单通知按原标题中的金额、紧急／异常文字及原到期提醒类型细分为金额待确认、异常与紧急事项、到期提醒、跟单待办；该细分仅用于呈现，不重新判断业务结果。未列前缀按原环节与处理类型归组。
- 分类数量累加组内原事项的 `item.count`，不使用明细数组长度替代，也不改变服务端结果。选中分类同时说明涉及数量与明细记录条数；明细每页 30 条，多页时底部显示页数、明细总数与前后页按钮。分类数量、明细条数和聚合业务记录数不能混用。
- 团队处理分布置于列表之后；人员按钮显示待核查事项数与异常事项数，点击切换对应负责人筛选，重复点击恢复全部。分布数据来自完整返回结果，不随当前类型、环节或搜索筛选重新计数。
- “监控依据与处理规则”默认折叠，展开提供数据、刷新、提醒时间、历史归属和原页面审批规则。
- 局部面板间隔 24px；桌面筛选四列，720px 以下改两列、标题和事项行动纵向排列，380px 以下筛选改单列。窄屏事项及人员按钮至少 44px 高。按钮、搜索框和下拉框提供 2px 蓝色可见键盘焦点。

## States and interactions

| 状态 | 界面行为 |
| --- | --- |
| 初次读取 | 显示读取提示，容器 `aria-busy`，刷新按钮显示“正在读取…”并禁用。 |
| 成功 | 显示范围、北京时间读取时间、真实来源状态及当前结果。进入页面与手动刷新触发读取；无轮询承诺。 |
| 首次失败 | 显示 `role="alert"` 错误及“重新读取”入口，不展示虚构结果。 |
| 刷新失败且已有结果 | 保留上次成功结果及其时间，并明确显示“当前显示上一次成功读取的结果”。 |
| 报价来源不可用 | 展示服务端“未配置”或“暂时无法读取”，并提示待接收报价可能不完整；不能据此宣称没有待接收报价。 |
| 最近检查无记录 | 显示“尚无记录”；不将读取时间当作每日检查完成时间。 |
| 筛选无结果 | 提示调整筛选；保留筛选控件。 |
| 已接入记录无事项 | 明确限定为当前已接入记录中没有匹配事项，不宣称全业务健康。 |
| 去处理 | 将事项交给既有 `openItem` 导航逻辑，在原业务页面处理。 |

## Data and permission boundaries

`lib/sales-monitor.ts` 提供只读 `GET sales-monitor`。服务端允许 sales、admin、ceo、management 角色，并按既有能力权限约束范围；前端隐藏负责人筛选不替代服务端授权。管理能力范围读取全团队，销售读取本人客户与项目、本人商务负责订单；团队分布仅在全团队结果中返回。

事项优先级为异常、待确认、到期提醒、待处理、历史对齐。来源包括新增客资首次联系、项目下一步、报价同步与接收、合同交接与订单关联、现有付款/特殊放行申请、已生成站内通知，以及已启用 WhatsApp 连接状态。连接检查只提示核查，不代发消息。

刷新只读取当前记录，不新建业务、重新生成到期通知或执行审批。到期提醒来自已存储的站内通知，每天北京时间 08:00 检查；08:00 后到期的事项在下次检查处理。读取时间与最近日检查时间必须分别呈现。

历史客资归属待对齐单独列示，不计入新增分配、待首次联系或首次联系逾期。未归属的聚合事项以管理者为处理提示，不能伪装为已分配给某位销售；团队人员分布不包含这类无人员归属事项。

报价接收、合同与跟单负责人确认、付款确认及 CEO 特殊放行继续使用既有业务页面及权限。监控页不增加批准、保存、自动修复、分配、消息发送或历史数据变更入口。

## Customer entry and ownership rules

`lib/customer-entry-monitor.ts` 与 `app/customer-entry-monitor.tsx` 提供固定六项客户核查：

| 规则 | 核查依据与边界 |
| --- | --- |
| 1. 历史／新增客资分类 | 按北京时间原始进入日期，以 2026 年 11 月 1 日为分界；日期缺失、无法确认、现有分类为日期待确认或与日期不符时提示核查。现有分类数量仅表示已保存的 cohort 元数据；即使现有分类为新增，也不能用它替代缺失的原始日期证据。 |
| 2. 历史归属未对齐或冲突 | 历史记录无归属、原负责人无法唯一匹配有效业务账号、原负责人与现负责人不一致或存在待核查标记时提示核对旧库及正式转交依据；不计新增分配与首次联系逾期。 |
| 3. 新增客资尚未分配 | 仅限现有分类为新增、原始日期明确且不早于分界、业务范围有效、无现负责人及原归属、无待核查标记和已发现重复问题的记录；待入档记录还须处于待分配状态。实际分配仍在既有客户管理共同队列流程执行。 |
| 4. 负责人异常 | 核查负责人编号失效、账号停用或角色不属于现有 sales、ceo、management 归属支持范围；提示管理员确认。 |
| 5. 疑似重复客户 | 按规范化电话、邮箱或公司名称给出人工核查依据；尊重已关联同一客户主体及已确认“同一客户／不同客户”的记录对，不重复当作未决问题。 |
| 6. 来源信息缺失 | 核查来源、必要 Meta 平台、有效业务范围、原始进入日期，以及已声明广告活动却缺失或失效的活动关联；只按证据补充。 |

“查看统计口径”默认折叠，展开后显示统计说明。区顶部的历史、新增、日期待确认数量是当前可见记录的现有分类统计，不是规则命中总数。同一记录可以命中多项规则，各项分别统计涉及记录，不能相加解释为唯一客户数或新增客资数。监控不自动重新分类、历史对齐、分配或合并，也不代用户确认身份核查结果。

独立只读端点 `GET sales-monitor/customer-rules?rule=1&page=1` 按规则读取明细，每页 20 条；与原事项列表分页分开。规则和页码由服务端校验，非法输入返回 400，写入方法拒绝；无命中时保留明确空态。读取时显示 `aria-busy` 和状态提示，失败显示警报及重试入口；旧请求结果不能覆盖后来选择的规则。明细仅导航至原客户或客户管理页面。

服务端按 `customers_all` 能力确定全团队或本人范围：本人范围仅含本人归属客户及本人创建的未入 CRM 客资池记录，重复核查及身份决定也限定在可见客户范围内，不暴露其他销售客户；全团队范围包含相应全部记录。前端展示范围不能替代服务端隔离。
